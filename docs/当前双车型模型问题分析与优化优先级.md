# 当前双车型模型问题分析与优化优先级

## 1. 文档目的

本文档记录当前项目中两个小车 USD 模型在 ROS 2 TF、传感器数据链路和车辆参考原点方面存在的问题，并给出建议的优化顺序。

分析对象：

- `assets/vehicles/roboracer_offroad.usd`
- `assets/vehicles/roboracer_max.usd`
- `scripts/configs/lariad_hard.yaml`
- `scripts/launch_lawn_mower_sim.py`

当前 `lariad_hard.yaml` 中启用的是 `roboracer_offroad.usd`，`roboracer_max.usd` 处于禁用状态。因此，现阶段 RViz 中看到的车辆、TF 和传感器数据主要来自 OffRoad 模型。

### P0 实施状态（2026-10-06）

以下 P0 修复已在启动时以组合 Stage 覆盖方式实现，不修改二进制 USD 源文件：

- OffRoad 的 `IsaacComputeOdometry` 已改为读取真实 Chassis；
- Depth Helper 指向不存在 Render Product 的悬空连接已移除；
- RGB、Depth 和 CameraInfo 已统一使用带命名空间的左相机 optical frame；
- 已建立 `map -> odom -> base_footprint -> base_link -> chassis/sensor` 语义 TF；
- `base_footprint -> base_link` 高度由轮胎包围盒和 Chassis 原点自动计算；
- ZED 相机和 IMU 外参由当前组合 Stage 自动提取；
- 原始 USD 中会发布错误 CAD/PhysX 原点的 TransformTree 已在图加载前停用。

### P1 实施状态（2026-10-06）

以下 P1 修复已经完成：

- 四个车轮不再使用重合的 Wheel 刚体原点，改为读取各轮胎视觉根 Mesh 的实时姿态；
- 四轮 frame 原点位于视觉轮轴中心，并继承悬架、转向和滚动姿态，以 30 Hz 发布动态 TF；
- OffRoad 已补齐 ZED 左右相机 mount/optical frame 和 ZED IMU frame；
- Max 已补齐 RealSense 彩色、左、右、深度相机的 mount/optical frame；
- Max 已补齐车体 IMU、RealSense IMU 和 OS2 LiDAR frame；
- RGB、Depth、IMU 和点云消息的 `frame_id` 已与实际 TF 对齐；
- 所有外参均从当前组合 Stage 的真实世界变换自动计算，不在 YAML 中重复硬编码数值。

运行时验收结果：OffRoad 和 Max 均生成 4 个位置互异且持续更新的车轮 TF；OffRoad 生成 7 条语义静态 TF，Max 生成 13 条语义静态 TF。已分别验证 `/opponent/rgb`、`/opponent/depth`、`/opponent/imu`、`/ego/imu` 和 `/ego/point_cloud` 的 `frame_id` 可在 TF 树中解析。

## 2. 总体结论

当前两个模型并不是完全不可用，主要问题是 USD/PhysX 物理结构与 ROS 坐标系和传感器消息语义没有严格对齐。

具体表现为：

1. 部分 CAD、Mesh 或 PhysX 刚体原点被直接作为 ROS Link 原点使用。
2. TF 树的父子连接关系大体存在，但部分坐标系的位置和轴向不符合 ROS/URDF 语义。
3. 启动脚本会修改消息中的 `frame_id`，但不一定同时创建对应的 TF。
4. YAML 中的传感器开关只能启用已有节点，不能创建模型中不存在的传感器或发布图。
5. 部分传感器虽然在 USD 中存在，但没有连接到 ROS 发布链路。
6. 部分 ROS 发布链路已经存在，但数据源、Render Product 或 `frame_id` 配置错误。

因此，后续优化应首先建立一套独立于 CAD/PhysX 原点的标准 ROS 坐标系，然后再修复深度图、里程计和传感器发布链路。

## 3. 两个模型共同存在的问题

### 3.1 CAD/PhysX 原点与 ROS Link 原点混用

模型内部可能同时存在以下几类原点：

- CAD 建模原点；
- 视觉 Mesh 原点；
- 碰撞体原点；
- PhysX 刚体质心或刚体原点；
- 关节局部坐标；
- 传感器 Prim 原点。

这些原点不一定满足 ROS 坐标系的标准语义。例如，ROS 中通常希望：

- `base_footprint` 位于车辆在地面的投影位置；
- `base_link` 位于车辆运动学参考点；
- `chassis_link` 表示真实车体刚体原点；
- 车轮 Link 原点位于各车轮旋转轴中心；
- 相机 Link 位于相机安装或成像中心；
- IMU Link 位于 IMU 测量中心；
- LiDAR Link 位于雷达扫描中心。

当前模型没有完整区分这些语义，从而导致 TF 树拓扑看似正确，但坐标系与可视模型的位置不一致。

### 3.2 车轮 TF 与车轮视觉几何不完全一致

当前轮子坐标系更接近物理刚体或关节原点，而车轮视觉 Mesh 可能还带有局部平移和旋转。因此可能出现：

```text
车轮 Link 原点 != 轮胎视觉几何中心
```

四个车轮坐标系处于相同高度本身不一定错误，因为四个轮轴中心通常就在同一个平面。真正需要检查的是：

- 每个坐标系是否位于对应轮子的轴心；
- 左右、前后轮的轴向是否一致；
- 车轮旋转轴是否与 RevoluteJoint 的轴重合；
- 视觉 Mesh 是否相对物理刚体带有额外偏移；
- 轮距、轴距和轮胎半径是否与模型外观一致。

### 3.3 修改 `frame_id` 不等于建立 TF

如果传感器消息使用：

```text
frame_id = lidar_link
```

则 TF 树中还必须存在：

```text
base_link -> lidar_link
```

否则 RViz 无法确定传感器相对于车辆的安装位置。当前启动逻辑对部分消息进行了 `frame_id` 重写，但传感器 TF 并没有全部同步补齐。

### 3.4 传感器开关与模型实际能力不一致

例如：

```yaml
enable_lidar: true
```

只能启用模型中已经存在的 LiDAR 和 ROS 发布节点。如果 USD 中没有 LiDAR Prim、Render Product 和点云 Helper，该选项不会自动生成点云传感器。

建议后续将相机总开关拆分为 RGB、Depth、Stereo 和 CameraInfo 等明确选项，并在加载模型时检查传感器能力。

## 4. `roboracer_offroad.usd` 存在的问题

### 4.1 深度图发布链路异常

OffRoad 模型的深度图 Helper 同时关联了：

- 一个有效的左相机 Render Product；
- 一个不存在或无效的 Render Product 节点。

这会造成深度数据源不明确，并可能导致：

- RViz 中深度图显示花屏或乱码；
- 深度数据格式或步长异常；
- Depth 与 CameraInfo 的分辨率不一致；
- 深度图使用了错误的相机 frame。

此外，模型虽然包含 ZED 左右相机，但目前主要只有左相机连接到有效的渲染和 ROS 发布链路，右相机没有独立图像输出。因此当前深度数据不能视为真正的双目深度计算结果。

### 4.2 里程计绑定到 ZED 组件

OffRoad 模型中的 `IsaacComputeOdometry` 当前读取 ZED 相机组件对应的刚体，而不是车辆真实 Chassis。

由于 ZED 固定在车体上，车辆的整体运动趋势仍然基本正确，但会带来以下问题：

- 里程计原点位于相机安装位置；
- 转弯时产生相机安装偏移对应的杠杆臂效应；
- `odom -> base_link` 的语义不准确；
- 与车辆控制和定位算法使用的参考点不一致。

应将里程计输入改为车辆 Chassis 或标准 `base_link` 所对应的刚体。

### 4.3 ZED IMU 有数据，但 TF 不完整

模型中存在 ZED XM 内部 IMU，ROS 发布图也会读取该 IMU，但还需要确保 TF 树包含：

```text
base_link
└── zed_link
    └── zed_imu_link
```

IMU 消息的 `frame_id` 必须与 TF 中的坐标系名称完全一致，不能只修改消息名称而不发布对应外参。

### 4.4 右相机没有独立输出

模型包含 ZED 左、右两个 Camera Prim，但右相机没有独立的 ROS Camera Helper 和 Render Product。因此当前不能发布标准双目相机数据组合，例如：

```text
/left/image_raw
/left/camera_info
/right/image_raw
/right/camera_info
```

### 4.5 模型中没有 LiDAR

OffRoad 模型没有发现：

- LiDAR Prim；
- RTX LiDAR Render Product；
- PointCloud ROS Helper。

因此，即使配置中设置 `enable_lidar: true`，也不应期望 `/opponent/point_cloud` 产生有效数据。

### 4.6 GNSS 是软件模拟数据

OffRoad 模型本身没有 GNSS Prim。GNSS 数据由启动脚本根据车辆世界坐标计算并通过桥接节点发布。因此它属于软件合成数据，不是 USD 中的物理传感器输出。

## 5. `roboracer_max.usd` 存在的问题

### 5.1 多个相机 Prim 没有完整接入 ROS

Max 模型包含：

```text
Camera_OmniVision_OV9782_Color
Camera_OmniVision_OV9782_Left
Camera_OmniVision_OV9782_Right
Camera_Pseudo_Depth
```

但当前发布关系为：

- Color Camera 已连接 RGB 发布链路；
- Left Camera 没有独立 ROS 输出；
- Right Camera 没有独立 ROS 输出；
- Pseudo Depth Camera 没有正确连接到 Depth Helper；
- Depth Helper 默认处于禁用状态；
- Depth Render Product 仍指向彩色相机，而不是 Pseudo Depth Camera。

因此，Max 模型虽然包含多个相机 Prim，但当前并不是完整可用的 RGB-D 或双目相机系统。

### 5.2 两个 IMU 中只有一个被发布

Max 模型中存在：

- Chassis/base_link IMU；
- RealSense 内部 IMU。

当前 ROS 图只读取车体 IMU。RealSense IMU 虽然存在，但没有独立 ROS 发布器、话题和完整 TF。

### 5.3 OS2 LiDAR 的 `frame_id` 错误

Max 模型包含 OS2 LiDAR，也存在点云发布链路，但当前点云使用 `base_link` 作为 `frame_id`。

这会让 RViz 和下游算法认为点云从车辆参考原点发出，而不是从 LiDAR 的真实安装位置发出。

应建立：

```text
base_link -> lidar_link
```

并将点云消息设置为：

```text
frame_id = lidar_link
```

也可以根据设备命名使用 `os2_link` 或 `os2_sensor`，但消息和 TF 必须保持一致。

### 5.4 CameraInfo 链路不完整

Max 模型没有发现清晰完整的 CameraInfo 发布链路。这可能导致 RGB 图像缺少对应的：

- 内参矩阵 `K`；
- 投影矩阵 `P`；
- 畸变参数 `D`；
- 与图像一致的分辨率和 `frame_id`。

### 5.5 里程计输入相对合理

Max 模型的 `IsaacComputeOdometry` 指向车辆 Chassis，这一点比 OffRoad 模型合理。但仍需通过独立的 ROS TF 校准 Chassis 与标准 `base_link` 之间的固定偏移。

### 5.6 GNSS 和雷达情况

Max 模型没有物理 GNSS Prim，GNSS 同样由启动脚本合成。模型中也没有发现毫米波雷达 Prim 和对应数据发布链路。

## 6. 建议的标准 TF 结构

建议两个模型统一使用以下 ROS 语义结构：

```text
odom
└── base_footprint
    └── base_link
        ├── chassis_link
        ├── front_left_wheel_link
        ├── front_right_wheel_link
        ├── rear_left_wheel_link
        ├── rear_right_wheel_link
        ├── camera_link
        │   └── camera_optical_frame
        ├── imu_link
        └── lidar_link
```

对于 ZED，可进一步细化为：

```text
base_link
└── zed_link
    ├── zed_left_camera_frame
    │   └── zed_left_camera_optical_frame
    ├── zed_right_camera_frame
    │   └── zed_right_camera_optical_frame
    └── zed_imu_link
```

对于 RealSense 和 OS2，可采用：

```text
base_link
├── realsense_link
│   ├── color_camera_frame
│   │   └── color_camera_optical_frame
│   ├── left_camera_frame
│   │   └── left_camera_optical_frame
│   ├── right_camera_frame
│   │   └── right_camera_optical_frame
│   ├── depth_camera_frame
│   │   └── depth_camera_optical_frame
│   └── realsense_imu_link
└── lidar_link
```

## 7. 优化优先级

### P0：建立统一的 ROS 坐标系规范

这是最高优先级，因为车轮、传感器、里程计和 RViz 显示都依赖 TF。

需要完成：

1. 明确定义 `base_footprint`、`base_link` 和 `chassis_link`。
2. 不再直接将 CAD/PhysX 原点作为最终 ROS 坐标系。
3. 为四个车轮创建位于轮轴中心的 Link frame。
4. 为每个实际发布数据的传感器创建对应 frame。
5. 明确所有坐标轴方向并符合 ROS REP-103 约定。

### P0：修复 OffRoad 深度图链路

需要完成：

1. 删除或断开无效 Render Product 连接。
2. RGB、Depth 和 CameraInfo 使用同一个有效相机数据源。
3. 保证图像分辨率、步长、编码和内参一致。
4. Depth 消息使用正确的 optical frame。
5. 明确深度编码使用 `32FC1` 还是 `16UC1`，并确保 RViz 按相同格式解释。

### P0：修复 OffRoad 里程计输入

将 `IsaacComputeOdometry` 的输入从 ZED 组件刚体切换到车辆 Chassis，并通过 TF 表达 Chassis 与标准 `base_link` 的固定偏移。

### P1：补齐传感器 TF 和正确的 `frame_id`

重点包括：

- OffRoad 的 ZED 相机和 ZED IMU；
- Max 的 RealSense 相机；
- Max 的车体 IMU和 RealSense IMU；
- Max 的 OS2 LiDAR；
- 所有 optical frame。

消息中的 `frame_id` 必须与实际发布的 TF 完全一致。

### P1：校准四轮坐标系

应结合以下信息确定车轮 frame：

- RevoluteJoint 的旋转轴；
- Joint 的 `localPos0` 和 `localPos1`；
- Chassis 和 Wheel 刚体的世界变换；
- 轮胎视觉 Mesh 的局部包围盒中心；
- 轮胎圆柱轴方向；
- 实际轮距、轴距和轮胎半径。

最终应满足：

1. frame 原点位于对应轮轴中心；
2. 指定轴与车轮旋转轴重合；
3. 左右轮的正转方向满足车辆前进方向；
4. 四个车轮相对于 `base_link` 的位置符合实际几何尺寸。

### P2：让配置文件反映模型真实能力

建议将笼统的开关拆分为：

```yaml
enable_rgb: true
enable_depth: true
enable_camera_info: true
enable_stereo: false
enable_imu: true
enable_lidar: false
enable_gnss: true
gnss_mode: simulated
```

不同车型应分别声明其能力。加载时如果配置要求的传感器不存在，应输出明确警告，而不是静默运行。

### P3：启用额外传感器

基础 TF、Depth 和 Odom 修复完成后，再考虑：

- 为 OffRoad 右相机增加独立发布链路；
- 为 Max 左右目相机增加发布链路；
- 启用 Max Pseudo Depth；
- 发布 Max RealSense IMU；
- 为 OffRoad 添加 OS2 LiDAR；
- 添加真实或仿真的毫米波雷达。

## 8. 推荐的实施顺序

建议按照以下顺序实施和验证：

1. 从 USD 中提取 Chassis、四个 Wheel Joint 和传感器 Prim 的世界变换。
2. 定义两个模型统一的 `base_link` 和 `chassis_link` 语义。
3. 校准四个车轮坐标系，并在 RViz 中检查轴心和轴向。
4. 修复 OffRoad 深度 Render Product 连接。
5. 将 OffRoad 里程计输入切换到 Chassis。
6. 建立 ZED、RealSense、IMU 和 LiDAR 的完整 TF。
7. 统一消息 `frame_id`、话题名称和 CameraInfo。
8. 增加启动时的传感器能力检查和错误提示。
9. 最后再启用目前未发布的右相机、双目、伪深度和第二个 IMU。

## 9. 验收标准

完成优化后，至少应满足以下条件：

1. RViz 中四个车轮坐标系位于各自轮轴中心。
2. 车轮坐标轴方向与实际旋转方向一致。
3. `odom -> base_link` 连续稳定，不使用相机安装点作为车辆运动参考点。
4. RGB、Depth 和 CameraInfo 时间戳、分辨率、frame 和内参一致。
5. Depth 图像不存在花屏、乱码和明显的步长错误。
6. IMU 数据使用真实 `imu_link`，并能在 TF 中转换到 `base_link`。
7. LiDAR 点云使用 `lidar_link`，点云在 RViz 中从真实安装位置发出。
8. 配置中关闭或模型不存在的传感器不会出现虚假的可用状态。
9. 当前模型没有的传感器会在启动日志中给出明确提示。

## 10. 当前最优先的三个任务

综合影响范围和当前已观察到的现象，最先应处理：

1. 建立独立于 CAD/PhysX 原点的标准 ROS TF 坐标系。
2. 修复 OffRoad 深度相机的无效 Render Product 连接及图像格式。
3. 将 OffRoad 里程计输入从 ZED 刚体切换到车辆 Chassis。

完成这三项后，才能从根本上改善车轮 TF 与模型不一致、深度图异常和里程计参考原点偏移问题。
