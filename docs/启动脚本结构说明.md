# 启动脚本结构说明

## 两个入口脚本的区别

| 文件 | 定位 | 默认配置 | 主要专有逻辑 |
| --- | --- | --- | --- |
| `scripts/launch_sim.py` | 通用 Isaac Sim 启动器 | `scripts/configs/pumptrack_simple.yaml` | 通用环境/车辆引用、基础传感器图、键盘控制、HUD、跟随相机、语义分割和仿真循环 |
| `scripts/launch_lawn_mower_sim.py` | LARIAD/割草机场景启动器 | `scripts/configs/lariad_easy.yaml` | 草坪场景根变换、车辆世界坐标变换顺序、语义 TF、轮轴中心校正、深度/CameraInfo/IMU/LiDAR 兼容修复 |

两者并不是两套完全独立的仿真程序。原先它们复制了大部分启动流程，导致公共问题需要在两个文件中同步修复。当前的拆分方式是：

```text
launch_sim.py                 通用场景专有逻辑 + 仿真循环
launch_lawn_mower_sim.py      LARIAD/割草机场景专有逻辑 + 仿真循环
tools/launch_common.py        公共启动引导层
tools/lawn_mower_tf.py        语义 TF、传感器能力和外参计算
tools/lawn_mower_physics.py   RoboRacer USD/PhysX 兼容修复
```

## 公共模块

`scripts/tools/launch_common.py` 负责以下内容：

1. 解析 `--config`、`--headless` 和 Isaac Sim 的额外参数；
2. 加载 YAML 配置并解析仓库根目录；
3. 设置 `RMW_IMPLEMENTATION`、`ROS_DOMAIN_ID` 和 CycloneDDS 网卡；
4. 查找完整 Isaac Sim Experience；
5. 配置 Tracy 性能分析器；
6. 创建 `SimulationApp`；
7. 配置渲染分辨率、DLSS、阴影、环境光遮蔽、反射和视口模式。

两个入口脚本通过 `bootstrap()` 获取这些公共初始化结果，命令行用法保持不变。

`scripts/tools/lawn_mower_physics.py` 负责 IMU 固定关节、悬架锚点、IMU 质量属性、LiDAR
质量属性等模型兼容修复；这些修复只作用于当前组合 Stage，不修改源 USD 文件。

## 当前仍保留在入口脚本中的内容

以下代码依赖具体模型或场景，不适合直接放入公共模块：

- USD 环境和车辆引用的变换顺序；
- RoboRacer 的 IMU、悬架、质量属性等模型兼容修复；
- LARIAD 模型的语义 TF 和传感器补链；
- 车辆控制、HUD、跟随相机、语义分割和主仿真循环。

这样可以避免把 LARIAD 专有的 TF 修复误应用到通用 Pumptrack 场景。

## 验证结果

- `python3 -m py_compile scripts/tools/launch_common.py scripts/tools/lawn_mower_tf.py scripts/tools/lawn_mower_physics.py scripts/launch_sim.py scripts/launch_lawn_mower_sim.py`：通过；
- 两个入口的 `--help`：通过；
- `git diff --check`：通过。

后续如果继续拆分，建议按“环境加载”“车辆加载与物理修复”“传感器图”“ROS 控制”“UI/HUD”“仿真循环”继续提取，并优先为每个模块增加独立的纯 Python 单元测试。

## `sensor_capabilities` 是否必须按车型配置

不是运行时必须项。启动器会扫描 USD Stage 中实际存在的相机、IMU、LiDAR 和雷达
Prim，再结合 `enable_*` 开关决定是否创建发布器；`sensor_capabilities` 目前主要用于
把配置声明与 USD 实际检测结果进行对比并输出告警。

不过当前 Max 和 OffRoad 的传感器能力确实不同：Max 有 RealSense IMU 和 LiDAR，
OffRoad 没有。因此如果保留这项“模型能力基线”，就应当为两款模型分别配置，当前
`lariad_hard.yaml` 的写法是合理的。若希望减少重复，可以把它移到按 USD asset
路径索引的车型 profile 中；不要把 Max 的能力声明复制到 OffRoad 上。

## TF 外参来源和车轮姿态说明

当前 TF 外参不是手工写在 YAML 中，而是在启动时从组合后的 USD Stage 计算：

- `base_link` 的运动参考：优先使用 `Rigid_Bodies/Chassis/base_link`；
- 里程计刚体：使用带 `RigidBodyAPI` 的 Chassis 子 Prim；
- 相机、IMU、LiDAR：使用各自传感器 Prim 的世界位姿相对 Chassis 的变换；
- `base_footprint -> base_link`：根据轮胎包围盒最低点计算底盘高度；
- 车轮平移：启动时读取轮胎视觉根 Mesh 的轮轴中心位置；
- 车轮 TF：轮轴中心位置固定使用 authored/YAML 外参；方向在启动时与 `base_link` 对齐，运行中只叠加 Wheel 刚体绕车辆 Y 轴的滚动角。

语义 TF 发现和外参计算已经移动到
`scripts/tools/lawn_mower_tf.py`，入口脚本只负责调用它；传感器安装外参通过
`/tf_static` 发布，车轮滚动通过 `/tf` 发布。`scripts/tools/drive_bridge.py` 会让轮子 TF 复用同车辆最新里程计时间戳，避免两套仿真时钟导致 RViz 间歇性缺少变换。

如果 RViz 中看到轮子相对于 `base_link` 存在航向角差，优先检查以下问题：

1. USD 中 Wheel 刚体的 CAD 局部轴是否与 ROS 轮子约定一致；
2. 轮胎视觉 Mesh 的显示旋转是否被误认为物理旋转；
3. RViz 显示的是轮子滚动姿态，还是固定安装外参；
4. 是否仍有 USD 内置 `PublishTransformTree` 同时发布同名 frame，造成 TF 冲突。

当前实现采用“YAML/authored 几何提供固定位置、Wheel 刚体提供滚动增量”：CAD 固定旋转和悬架平移不会污染 `wheel_link` 外参，实际滚动仍可在 RViz 中显示。若后续需要表达前轮转向，应额外增加 steering frame，再把滚动 frame 挂到 steering frame 下。

### YAML 外参覆盖

默认情况下，启动器从组合后的 USD Stage 读取 Chassis、轮胎和传感器 Prim 的世界位姿，再换算成相对语义 `base_link` 的外参。每辆车可以通过 `tf_extrinsics` 覆盖自动计算结果：

```yaml
tf_extrinsics:
  # 语义 base_link 在 CAD Chassis 坐标系中的四轮几何中心。
  base_link_center_xy: [0.116725, 0.030074]
  # base_footprint 到 base_link 的垂直距离。
  base_link_height: 0.050056
  frames:
    front_left_wheel_link:
      xyz: [0.088910, 0.136256, 0.001561]
      quaternion_xyzw: [0.0, 0.0, 0.0, 1.0]
```

`frames` 中的 `xyz` 和姿态均相对于语义 `base_link`。姿态可以使用 `quaternion_xyzw`，也可以使用 `rpy_deg`。YAML 中已定义的 frame 优先使用配置值；未定义的相机、IMU、LiDAR 等外参继续从 USD 自动推导。

`tf_settings.zero_odom_at_start` 启用后，启动器会在
`odom_zeroing_duration_s` 指定的物理落地窗口内持续校准局部里程计原点。窗口结束时 `odom` 与语义 `base_link` 重合，此后 `odom` 保持固定，车辆运动由动态 `odom -> base_footprint` 表达。
